# Firebase setup (required for online features)

The repository deliberately does not contain project credentials. Until the Firebase project values are configured, the app displays a setup screen and does not attempt anonymous or demo sign-in.

## 1. Create the Firebase project

1. Open https://console.firebase.google.com/ and create/select a project.
2. Add an Android app with package name `com.finora.finora` only if that is the package generated by the current workflow. Confirm the final application ID in the APK build log before registering it.
3. In **Authentication → Sign-in method**, enable **Email/Password**.
4. Create a **Cloud Firestore** database.

## 2. Set GitHub Actions secrets

In GitHub, open **Settings → Secrets and variables → Actions → New repository secret**. Add these values from Firebase project/app settings:

- `FIREBASE_API_KEY`
- `FIREBASE_APP_ID`
- `FIREBASE_MESSAGING_SENDER_ID`
- `FIREBASE_PROJECT_ID`
- `FIREBASE_IOS_APP_ID` (required for a working iOS app; use the registered iOS Firebase app ID)
- `FIREBASE_IOS_BUNDLE_ID` (required for iOS; for this project use `com.finora.finora` unless you deliberately register a different bundle ID)
- `GOOGLE_SERVER_CLIENT_ID` (the Google Cloud **Web application** OAuth client ID for Drive API access)
- `GOOGLE_IOS_CLIENT_ID` (the Google Cloud **iOS** OAuth client ID; required for Google Sign-In on iOS)

Optional for web builds: `FIREBASE_AUTH_DOMAIN`. Register the iOS app in the same Firebase project and supply both iOS values before using the app on an iPhone or iPad.

The API key is client configuration, not a substitute for database security. Never commit service-account JSON, OAuth client secrets, or admin credentials.

## 3. Deploy security rules

Review `firestore.rules`, then deploy them with Firebase CLI from the repository root:

```sh
firebase login
firebase use --add
firebase deploy --only firestore:rules
```

The rules are a baseline and should be exercised against the Firebase Emulator before production use. Review access rules again if you add admin roles, transaction approvals, or exports.

## 4. Stable Android release signing (Google OAuth SHA-1)

The Android workflow supports a persistent release keystore. The keystore and `android/key.properties` are created only on the GitHub Actions runner and are ignored by git; never commit either file.

Create the keystore once on a trusted computer with Java's `keytool` installed. Keep the keystore and passwords in a safe backup. Do not regenerate it for each build:

```bash
keytool -genkeypair -v -keystore finora-upload.jks -alias finora -keyalg RSA -keysize 2048 -validity 10000
```

Use a strong keystore password and key password. For the simplest setup, you may use the same password for both. Convert the keystore file to a single-line Base64 value:

- Linux/macOS: `base64 -w 0 finora-upload.jks` (on macOS, use `base64 finora-upload.jks | tr -d '\\n'`)
- Windows PowerShell: `[Convert]::ToBase64String([IO.File]::ReadAllBytes("finora-upload.jks"))`

In the repository, open **Settings → Secrets and variables → Actions → New repository secret** and add:

- `ANDROID_KEYSTORE_BASE64`: the complete Base64 output from the previous step
- `ANDROID_KEYSTORE_PASSWORD`: the keystore password
- `ANDROID_KEY_ALIAS`: `finora` (or the alias you chose)
- `ANDROID_KEY_PASSWORD`: the key password

After saving all four secrets, run **Actions → Build Android APK → Run workflow**. The workflow prints the signing certificate SHA-1 in the **Print release certificate SHA-1** step. Copy the SHA-1 value from that log; never copy or print the keystore or its passwords.

In Google Cloud Console, open **Google Auth Platform → Clients → Create client → Android** (or edit the existing Android OAuth client). Set package name to `com.finora.finora` and paste the SHA-1 fingerprint. Save the client. The package name and SHA-1 must match the APK that you install. If an app has already been published with a different signing key, do not switch keys without checking the existing distribution/signing setup first.

If the four signing secrets are not configured, CI warns and continues with the temporary generated signing configuration. That fallback is only for build checks; it does not provide a stable SHA-1 for Google Sign-In.

## 5. Build an APK

After adding the GitHub Actions secrets, open **Actions → Build Android APK → Run workflow**. The workflow passes the values as Dart compile-time definitions and uploads an APK artifact when the build succeeds.

For a local build, provide the same `--dart-define` values to `flutter build apk --release`.

## Current implementation notes

- Email/password registration and login use Firebase Authentication.
- Mess records and personal transactions are stored in Firestore; Firestore snapshots provide live synchronization.
- Receipt images are uploaded to the signed-in user's Google Drive. Mess receipt files are shared with the Google account emails recorded in the mess member profiles; each member must open the app at least once after this update so their email can be added to the shared profile.
- Google Drive OAuth requires enabling the Google Drive API in Google Cloud Console, configuring an OAuth consent screen, creating a Web application OAuth client ID, and registering the Android app's package/signing SHA-1 as an Android OAuth client. Add the Web client ID as GitHub Actions secret `GOOGLE_SERVER_CLIENT_ID`.
- For iOS, create an iOS OAuth client ID for the registered bundle ID and add it as `GOOGLE_IOS_CLIENT_ID`. The iOS workflow writes the client ID and its reversed URL scheme into the generated `Info.plist`. The unsigned iOS CI build is only a compile check; actual sign-in still needs a real device test.
- The CI workflow generates platform folders on each run. For reliable Android Google Sign-In, use a stable signing certificate and register its SHA-1 with the matching Android OAuth client; a CI-generated debug signing key can change between runs. The app requests the `drive.file` scope and creates receipt files in the signed-in user's Drive.
- The Google account used for Drive access may differ from the email/password account used for Finora. Mess receipt sharing only works if the email in the member profile matches a Google account the member can access.
- Loans and repayment events are stored under the signed-in user's private path.
- Daily per-member meal counts are stored under each mess; the same member can update their count for a given day.
- Food-related expenses can be explicitly marked as meal-rate eligible. Monthly meal rate is eligible food expense divided by total counted meals.
- Mess owners can choose the default strategy used on new expense records: equal, meal-count-based, or payer-accounted. Mess expenses start pending and are included in balances only after owner approval; owners can also assign fixed member amounts or percentage-based shares.
- The signed-in member's shared display profile is backfilled when the member-balance view loads. Other members' private user documents are never read for names.
- A mess owner can close a month once. The closure stores a month-keyed cumulative member-balance snapshot and month totals; the balance view starts from the latest closure and adds transactions dated after that closed month.
- Firestore rules make month closures read-only after creation and prevent transaction edits/deletes through the current client. Deploy and test these rules before production use.
- Reports can be filtered by month before PDF/XLSX export. PDF exports embed Noto Sans Bengali for Bengali labels and descriptions.
- PDF and XLSX exports are generated on-device and shared using the platform share sheet.
- The iOS workflow validates an unsigned iOS build on macOS. An unsigned build is not ready for TestFlight/App Store distribution; signing and Apple developer configuration are still required.
- Personal finance is private by default. Do not add personal transaction data to shared mess collections.
- This is an initial implementation. Test rules and multi-user access with two test accounts before using real financial records.


## Firestore rules regression tests

The repository runs the Firestore emulator rules tests through GitHub Actions (`Firestore Rules Tests`). To run locally, install Node.js 20+, Java 17+, and npm dependencies, then run:

```bash
npm install
npx --yes firebase-tools emulators:exec --only firestore --project demo-finora-rules "npm test"
```

The tests verify that closed months reject new ledger transactions and meal changes, open months accept valid writes, and a member cannot read another user's private document. The app stores a `monthKey` (`YYYY-MM`) on every new mess transaction and meal entry; do not remove this field from client writes.
